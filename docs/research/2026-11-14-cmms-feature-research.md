# ShiftFix: CMMS workflow research for the final hackathon day

Researched: 2026-11-14. Sources: first-party product help and documentation from MaintainX, UpKeep, Limble and Fiix, with IBM meter documentation for a narrow edge case. This is workflow research, not a code audit, vendor evaluation or production-readiness certification. Vendor availability varies by platform, account configuration and subscription; no pricing or performance claims are used here.

## Recommendation

Spend the remaining day connecting existing modules into one convincing factory workflow: **failed inspection → manager-reviewed repair request → part issued against the job → repair evidence and verification → next-shift handover**. Add asset QR entry if the critical path is stable. The app already has a broad catalog surface; these connections make that surface useful during actual maintenance.

This prioritization is an inference from the documented ShiftFix baseline and the workflows below, not a claim that competitors lack these features. A deterministic handover with links to evidence, explicit outstanding blockers and a visible acknowledgment can differentiate the demo through clarity. No AI summary is necessary for this behavior.

Do not equate every catalog with a complete maintenance workflow. Inventory is more useful when an issue names the work order; an inspection is more useful when a failure has an owner and a linked follow-up; a dashboard is more useful when the next shift can distinguish an unresolved breakdown from completed work awaiting verification.

## Baseline and evidence boundaries

Read locally: [operations guide](../operations-guide.md) and [demo-data disclosure](../demo-data.md). Their statements are the sole basis for the ShiftFix status column below. **Code and live behavior were not audited for this research.** “Missing” means not documented, not proof that code cannot support it. “Partial” means a related capability exists but the full workflow is not documented. “Present” means the stated narrow behavior is documented.

The operations guide describes a single-factory workspace, role checks, request/repair/verification workflow, optimistic concurrency, private repair images, inventory adjustments and atomic receiving, every-N-days recurrence, manual meter thresholds, immutable inspection responses, CSV tools, reversible archive and access-scoped reporting. It explicitly says teams do not grant access and monitoring has no live sensor connection.

The demo guide describes 177 fictional jobs spanning 62 dates, 18 populated catalog kinds, 8 display-only people, 6 paused plans and 3 paused rules. These records are valuable for a walkthrough, but do not demonstrate real sign-ins, real sensor ingestion, real suppliers or real maintenance outcomes. Existing demo people cannot receive new live assignments. Preserve the visible fictional-data disclosure when demonstrating any new workflow.

## A realistic final-day cut

These are **engineering estimates**, not measured implementation times or vendor promises. They assume one person familiar with the existing code, reuse of current authorization/concurrency patterns, no new external integration, and no architectural rewrite. Audit the actual extension points before committing. Build one coherent vertical slice and reserve verification time.

| Order | Deliverable | Estimate | Completion boundary |
| --- | --- | --- | --- |
| 1 | Job-linked part issue/return | 2.5–4 hours | Issue from a job; quantity and movement updated atomically; retried issue cannot consume twice; return references original issue; job shows history. Reservations are stretch. |
| 2 | Inspection exception follow-up | 1.5–2.5 hours | Submit immutable response; create/reuse one review request per failed item or one clearly grouped request per response; bidirectional evidence links; no automatic approval. |
| 3 | Shift handover view | 1–2 hours | Team/time filter, active carried-over work, completed work, pending verification, explicit blockers, next action and source links; printable/exportable summary. |
| 4 | Verification and demo rehearsal | 2 hours minimum | Two roles, concurrent stock test, repeated submission/retry, failed checklist, overnight shift boundary, mobile and keyboard walkthrough, all fictional labels retained. |
| Stretch A | Printable asset QR/deep link | 0.5–1 hour | Known asset URL survives login; prefilled request displays asset confirmation; QR carries no credentials. |
| Stretch B | One-open-incident meter guard | 1–2 hours | Different above-threshold readings link to the same unresolved incident; history says why suppressed; normal/re-cross behavior explicit. |
| Stretch C | Manual labor and downtime entry | 2–4 hours | Separate duration and outage concepts, validated values, corrections with audit; no inferred historical costs. |

The first three plus verification total **7–10.5 hours estimated**. If the working day is shorter, deliver part issue plus handover and verification, then add inspection linkage only if time remains. Do not add all stretch items just because they are individually small. Full reservations add approximately **2–4 additional hours estimated** beyond an issue ledger because allocation competes across jobs; they should replace a core item if selected.

Recommended demo, approximately three minutes: scan or open an asset → fail one inspection item → see its review request → manager accepts/assigns → worker issues one known part and submits repair evidence → manager verifies → handover shows the resolved incident and one separate still-blocked job. New assignments must use a real authorized identity, not one of the 8 display-only demo people. No email, supplier message or external write is needed for this demonstration.

## Proposed factory acceptance cases

The cases below are **recommended ShiftFix product contracts** derived from the cited workflows. They are not assertions that every vendor implements these policies. Adopt only the cases for features actually built; retain the rest as backlog acceptance criteria.

### A. Inventory linked to work

1. **Atomic consumption:** with stock 3, issue 2 to job A; stock becomes 1 and exactly one movement links part, job, actor, quantity and reason. Simulate failure during commit: both ledger and quantity change together or neither changes.
2. **Concurrent shortage:** two technicians each issue 2 from stock 3. Exactly one succeeds; the other receives a refreshable conflict/shortage, and the balance never becomes negative.
3. **Retry safety:** retry an identical issue command after a timeout. Return the original outcome without another decrement. Reusing that command key with different quantity is rejected.
4. **Return ceiling:** return 1 of 2 issued, then attempt to return 2 more. The second action fails because outstanding issued quantity is 1. Corrections reference the original issue rather than rewriting it.
5. **Historical integrity:** archive a part or job after issue. The movement retains the original code/name, actor and job reference; new issues to archived records fail.
6. **Compensating correction:** a defective part returned to the storeroom and a return to supplier are distinct movements. Reversing the repair's consumption must not silently undo a purchase receipt.
7. **Reservation semantics, if built:** starting stock 5, reserve 3 for A: on-hand remains 5, available becomes 2. Another job cannot reserve 3. Issue A's 3: on-hand becomes 2, committed becomes 0, available remains 2. Cancel A before issue: release reservation without increasing on-hand.
8. **Reservation lifecycle:** lowering a planned quantity releases only the difference; increasing it performs a fresh availability check. Rejected/merged/skipped jobs release unissued reservations once. Reopening does not repeat past consumption.
9. **Adjustment below commitment:** stocktake attempts to lower on-hand below reserved quantity. Reject it with allocation details or require an explicit supervised reconciliation; do not silently invalidate other jobs' readiness.
10. **Cost snapshot, if built:** issue 2 at unit cost 100; later catalog cost changes to 120. Historical job part cost remains 200. Record currency and rounding; unknown cost is distinguishable from zero.

These contracts follow the allocation/issue distinction in [MaintainX parts statuses](https://help.getmaintainx.com/part-statuses-and-part-availability), the job-specific cost concept in [MaintainX fields](https://help.getmaintainx.com/work-order-form-fields), and the separate return paths in [Fiix returns](https://helpdesk.fiixsoftware.com/hc/en-us/articles/115002779983-Managing-parts-returns-adjusting-receipts). They deliberately choose stricter no-overcommit behavior for the prototype rather than copying a warning-only interaction.

### B. Inspections and repair closure

11. **Failure provenance:** a failed “guard intact?” item creates a review request containing asset, response ID, stable item ID/text, answer, observation and evidence references; opening either record reaches the other.
12. **One exception, one decision:** double-tap or retry “create follow-up” yields one request. If several items are grouped into one request, the UI lists all included failures. A future inspection run is a new response and may create a new incident.
13. **N/A is explicit:** an unanswered required item cannot be submitted. N/A is not silently counted as Pass; require a reason when the chosen inspection policy needs one.
14. **Template revision:** edit/reorder/archive a template after a response was submitted. The old response still renders its original item text/order and version, and links still point to the correct failed item.
15. **Role boundary:** a Worker may submit a permitted inspection/follow-up, but cannot make it approved by modifying a request body. Follow-up creation uses the same server authorization as ordinary requests.
16. **Evidence failure:** upload fails or network drops on submit. Show saved/unsaved state precisely; do not leave a “completed” inspection with silently missing required evidence.
17. **Failure is not remediation:** completing the inspection records its result. It does not close the corrective repair, change Fail to Pass or imply that the machine is safe to operate.
18. **Review return:** manager requests more evidence; original immutable response remains intact while additional corrective-work evidence is recorded on the job.

These recommendations build on [MaintainX corrective work](https://help.getmaintainx.com/trigger-a-work-order), [required/assigned procedure fields](https://help.getmaintainx.com/procedure-fields) and [Limble approval instructions](https://help.limblecmms.com/en/articles/8594196-advanced-task-instruction-types). A checklist sign-off is evidence of a recorded decision; do not describe it as a certified safety permit.

### C. Shift handover and QR

19. **Overnight shift:** define a shift from 22:00 Nov 14 to 06:00 Nov 15 in the factory timezone. Use a half-open interval `[start,end)` for activity so an event at 06:00 appears once across adjacent shifts.
20. **Carryover is visible:** a critical job opened yesterday with no activity this shift still appears under unresolved carryover. Activity-only filtering must not hide it. Completed-this-shift and still-open are separate sets.
21. **Status as of:** show when the handover was generated and whether it is a live view or snapshot. A later job update must not silently rewrite an acknowledged historical snapshot.
22. **Useful blockers:** “waiting for part,” “waiting for access” and “awaiting verification” include an owner and next action. “In progress” alone is not a sufficient handover note.
23. **Audience authorization:** report, source links, CSV and print output use the viewer's allowed records. Team filtering must not grant access through descriptive team membership.
24. **Acknowledgment, if built:** a receiving real user acknowledges a specific revision/time window; editing the handover afterward creates a new revision or visibly invalidates that acknowledgment.
25. **Authenticated QR:** scan before login; sign in and return to the intended asset. Confirm asset code/name before submission. Unknown/archived code yields a clear unavailable message, never a fallback to a different machine.
26. **QR is a locator:** copying a QR does not grant access. Reject an unauthorized asset ID at the API. Printed tags contain a stable locator, not a token, private image URL or mutable display name.
27. **Camera unavailable:** permission denied or desktop browser still allows entering/searching the asset code. The QR request route works without writing a custom camera scanner.

The handover source is [MaintainX shift summary](https://help.getmaintainx.com/end-of-shift-summary); its documented scheduled summaries cover the previous day, so overnight shift behavior above is a deliberate ShiftFix requirement, not copied vendor behavior. The intake source is [MaintainX QR/barcode workflows](https://help.getmaintainx.com/about-qr-codes-and-barcodes).

### D. Meters and preventive maintenance

28. **Different readings, same incident:** enter 81, 82 and 83 against an above-80 rule with different reading IDs. One unresolved incident exists; each suppressed evaluation records its reason and links the incident. Same-reading retry remains separately idempotent.
29. **Threshold edges:** document whether “above 80” means `>80` or `>=80`. Exercise 79.9, 80 and 80.1, low threshold equivalents, missing unit, NaN/infinity and a value outside the supported range.
30. **Rearm:** for a latched high rule, sustained high values do not re-fire. A normal reading followed by a high one starts a new incident only according to the chosen open-incident policy. If adding hysteresis, expose the clear threshold separately.
31. **Out-of-order reading:** a backdated reading does not become “latest” just because it arrived last or retrigger resolved historical incidents. Either reject historical automation evaluation explicitly or define it separately from recording history.
32. **Counter reset:** a cumulative hours meter moves from 12,800 to 10 after replacement. Require an explicit reset/replacement event with reason; preserve lifetime usage separately. Do not treat this as negative operating hours or infer a rollover from any lower value.
33. **Rollover:** if a counter cycles every 10,000 units, a transition 9,990 → 5 adds 15. Store counter modulus semantics explicitly; “maximum displayed value” 9,999 and rollover modulus 10,000 are different inputs.
34. **Fixed cadence:** weekly Monday PM completed Thursday still targets the next Monday; completing early does not move the anchor. Pausing/unpausing has an explicit missed-occurrence policy.
35. **Completion cadence:** “7 days after completion” completed Thursday targets the following Thursday; rejection, return for evidence or provisional repair submission does not count as verified completion unless that is the deliberately chosen rule.
36. **Calendar edges:** monthly 31st, leap day, timezone changes and daylight saving have explicit clamp/skip rules before those schedules are exposed. A daily calendar time is not necessarily 24 elapsed hours.
37. **Catch-up burst:** advance a usage reading over several service milestones. Choose one coalesced request with missed-count metadata or one per milestone, and label the policy; preserve the app's current coalesced calendar behavior unless intentionally changed.
38. **Time OR usage:** simultaneous calendar and usage satisfaction creates one occurrence. Define whether both next thresholds reset on creation or completion; a completion must not advance unrelated PM plans.
39. **Plan edits:** changing interval/asset/assignee affects future work under a new plan revision; already-created occurrences retain their original provenance. Concurrent edits/generation cannot create duplicate occurrence IDs.
40. **Paused demo rule:** entering demonstration readings for a paused rule records history without activating future work. Explicitly enabling it is a separate real action.

Evidence: [MaintainX duplicate suppression](https://help.getmaintainx.com/faq-automations), [condition/rearm options](https://help.getmaintainx.com/set-up-condition-based-maintenance), [MaintainX fixed/floating](https://help.getmaintainx.com/about-maintenance-plans), [Fiix anchor semantics](https://helpdesk.fiixsoftware.com/hc/en-us/articles/210110666-About-fixed-and-floating-triggers), and [Limble missed usage occurrences](https://help.limblecmms.com/en/articles/6989116-pm-scheduling-options). IBM explicitly distinguishes rollover readings from ordinary lower readings and recalculates dependent history/PM when histories change: [adding readings](https://www.ibm.com/docs/en/masv-and-l/maximo-manage/cd?topic=locations-adding-meter-readings), [history rules](https://www.ibm.com/docs/en/masv-and-l/maximo-manage/cd?topic=overview-update-meter-history-rules). Counter modulus and epoch handling above are proposed design choices.

### E. Labor, downtime, offline and site boundaries

41. **Labor versus outage:** two technicians each work one hour on the same one-hour outage. Labor is two person-hours; downtime is one asset-hour. Waiting for parts may extend downtime without increasing wrench time.
42. **Downtime intervals:** reject end before start; distinguish planned/unplanned; avoid double-counting overlapping incidents on one asset. An open outage accrues only to the report's as-of time and is visibly open.
43. **Rate snapshot:** an administrator changes a worker's current rate. Past labor entries retain their recorded rate/currency; corrections are new audited changes. Unknown rate does not become a false zero cost.
44. **Metric prerequisites:** show MTTR/MTBF as unavailable when failure classification, observation period or operating hours are absent. Do not derive them from the 177 fictional job timestamps or assume 24/7 operation.
45. **Draft survives disconnect:** create a report draft, reload offline and reconnect. Preserve text and supported attachments, display “not submitted,” and use a persistent command ID on eventual submit. A successful local save must not look like server approval.
46. **Conflict on reconnect:** manager reassigns/closes a job while technician is offline. Revalidate role, record version and allowed transition; show a resolvable conflict. Do not replay stock changes or overwrite verification from a stale local copy.
47. **Storage/user switch:** browser storage is full or user logs out/switches identity with a pending draft. Warn about unsaved content and prevent another user reading private cached records. Do not persist authentication tokens inside draft content.
48. **Multi-site later:** a user allowed at site A guesses a site B job/asset/image/export ID. Every read/write and signed file authorization must deny it; selectors and hidden navigation alone cannot enforce this boundary.
49. **Role revocation:** a worker loses access after loading a view. The next mutation/export/upload authorization is rejected using current permissions, consistent with the existing documented backend identity rechecks.

Labor/cost evidence: [UpKeep job costs](https://help.onupkeep.com/en/articles/4925963-how-to-calculate-time-cost-to-a-work-order), [time entry](https://help.onupkeep.com/en/articles/4712446-how-to-record-time-to-a-work-order). Reliability evidence: [Limble downtime](https://help.limblecmms.com/en/articles/3006463-tracking-downtime). Offline evidence: [MaintainX cache boundaries](https://help.getmaintainx.com/offline-mode), [UpKeep offline work](https://help.onupkeep.com/en/articles/4712557-how-to-use-upkeep-offline). Site evidence: [Limble access versus organization hierarchy](https://help.limblecmms.com/en/articles/8828169-locations-vs-parent-assets). The conflict, privacy and numerical policies above are recommended requirements; the retrieved offline pages do not establish vendors' conflict-resolution algorithms.

## Source-annotated notes and caution when borrowing behavior

- **MaintainX inventory:** allocation and physical issue are separate state changes. Its documented overcommit flow offers remediation/warnings; copying the labels does not prove ShiftFix prevents oversubscription. [Parts statuses](https://help.getmaintainx.com/part-statuses-and-part-availability). For a one-day implementation, enforce a simpler no-overcommit invariant.
- **MaintainX corrective action:** failure prompts occur when completing the parent work order, rather than proving every failed answer instantly creates a separate repair. [Work-order triggers](https://help.getmaintainx.com/trigger-a-work-order). ShiftFix should explicitly choose manual follow-up versus automatic review request creation.
- **MaintainX handover:** team/user and selected time-range scope matter. Scheduled runs analyze the previous day only. [End of Shift Summary](https://help.getmaintainx.com/end-of-shift-summary). The proposed overnight carryover/acknowledgment behavior is additional product design.
- **MaintainX automation:** a duplicate-reading idempotency key solves retry duplication, while rerun/open-job policies solve different readings against a persistent condition. [Automations FAQ](https://help.getmaintainx.com/faq-automations). The source describes a default five-minute rerun interval; do not blindly adopt that interval for a factory warning.
- **MaintainX condition filtering:** rearm, multiple-readings and duration-based choices address different noise patterns. [Condition-based setup](https://help.getmaintainx.com/set-up-condition-based-maintenance). A temperature spike during startup should be demonstrably treated according to the configured policy, not described as predictive failure detection.
- **UpKeep cost:** labor, parts and additional expenses are distinct cost sources. [Time and cost](https://help.onupkeep.com/en/articles/4925963-how-to-calculate-time-cost-to-a-work-order). Application hosting usage in ShiftFix Billing is a separate concept from maintenance job cost.
- **UpKeep offline:** its guide explicitly distinguishes editable status/activity/checklists from viewable due date, description, parts and asset/location, and describes cached/bookmarked work plus offline drafts. [Offline guide](https://help.onupkeep.com/en/articles/4712557-how-to-use-upkeep-offline). This is evidence to publish a capability matrix, not promise every operation works offline.
- **MaintainX offline:** cache creation requires connectivity; switching organizations requires connectivity and a refreshed organization-specific cache. [Working Offline](https://help.getmaintainx.com/offline-mode). Neither this page nor UpKeep's guide establishes how all concurrent edit conflicts are resolved.
- **Limble reliability:** operating hours are an explicit input, with a documented default of 40 hours/week. [Tracking Downtime](https://help.limblecmms.com/en/articles/3006463-tracking-downtime). ShiftFix should request operating assumptions instead of silently importing that default.
- **Limble PM:** missed usage/threshold intervals can generate multiple PMs after a new reading; time-or-usage uses specific schedule/reset settings. [PM Scheduling Options](https://help.limblecmms.com/en/articles/6989116-pm-scheduling-options). ShiftFix's documented coalesced overdue strategy is therefore a policy choice, not universally equivalent PM behavior.
- **Fiix trigger terminology:** floating meter schedules normally move from the reading that generated the job; a closure-based option changes the anchor. [Fixed/floating triggers](https://helpdesk.fiixsoftware.com/hc/en-us/articles/210110666-About-fixed-and-floating-triggers). Contrast with completion-anchored [MaintainX floating plans](https://help.getmaintainx.com/about-maintenance-plans); terminology alone is insufficient for acceptance tests.
- **Fiix inventory history:** used stock locations cannot be deleted when doing so would remove their historical work-order associations; deactivation is the stated alternative. [Stock locations](https://helpdesk.fiixsoftware.com/hc/en-us/articles/210108806-Add-or-remove-stock-from-a-location). This supports preserving ShiftFix's existing reversible archive approach as new ledgers are added.
- **IBM meters:** continuous meter reset/replacement is a distinct action, not an arbitrary low reading.
